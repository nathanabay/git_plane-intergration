## Findings

### F1 [MAJOR] Production authorization permanently rejects GitHub-queued reducer continuations
File: src/app/mappings.ts:92
Spec: §6, §7.1, §7.3, §7.4, §7.6
Evidence: A normal authorized QLL-NEW PR registers its original resume_reducer on side github (`pr.ts:100`), with continuation.mappingId but no installationId or repoId. createOutboundAuthoriser takes the side === github branch first, converts the absent installationId to NaN and throws at assertInstallationAllowed (`mappings.ts:75-77,93`). The resume_reducer branch at :97 is unreachable. main.ts:118 wires this authorizer, and outbox.ts:505-506 turns the refusal into a terminal 403 before resume dispatch at :559-562. The item/link/created audit succeed, but the original opened rule, rollup and linkback never run; retryFailed also refuses that same template. Plane-to-GitHub events fenced during creation have the same defect: mirror.ts:99 registers a GitHub-side resume containing only the continuation. The CA end-to-end fixture constructs its outbox without authoriseWrite (`tests/app/review-r5-ca.test.ts:22-27`), while CD's authorizer fixture never dispatches the actual PR resume.
Fix: Authorize resume_reducer by its stored continuation mapping/workspace before branching on destination side, on both execution and reset. Preserve checks for actual GitHub API writes. Exercise the real PR create and Plane-to-GitHub deferred event with createOutboundAuthoriser installed, including failure/replay and revocation.

### F2 [MAJOR] Smart Commit authorization requires a SHA claim that is written after jobs become executable
File: src/app/mappings.ts:107
Spec: §4, §5, §7.2, §7.6
Evidence: Every new Smart Commit intent is tagged _smartCommit during registration (`outbox.ts:262-263`), and enqueue commits it then calls wake, which adds a runnable outbound job (`:169,274,293`). The production authorizer refuses that intent unless processed_commits already contains its SHA/workspace (`mappings.ts:105-108`). processPush claims the SHA only after all command/key lookups and registrations finish (`smart-commits.ts:391-439`). Concrete schedule: an authorized push contains QLL-1 #comment one and QLL-2 #comment two; after the first intent wakes, the independent outbound worker executes it while the inbound reducer awaits the second identifier lookup. No claim exists, so the first command is marked failed immediately as authority_refused. If the second lookup is transiently unavailable, :434-436 returns for retry without ever claiming, making the denial possible even after that inbound attempt ends. Later claiming does not revive the failed first row; its registered step is skipped on ordinary retry. The new Smart Commit test drains only after run(original) and omits the authorizer (`tests/github/review-r5-cb.test.ts:21-35`); CD pre-seeds the claim (`tests/app/review-r5-cd.test.ts:142`).
Fix: Store the authorized source repository/installation/workspace with each command intent when registering it, and validate that immutable authority without requiring the final completion claim. Alternatively make ownership establishment and outbox admission atomic while preserving partial-step retries and once-only SHA semantics. Cover outbound execution between two registrations and a transient later-key lookup.

### F3 [MAJOR] Two projects in one workspace are incorrectly treated as ambiguous GitHub ownership
File: src/operations/outbox.ts:185
Spec: §7.3, §7.4, §8
Evidence: The mapping API allows the same repo/installation/workspace to map to two different Plane projects; its duplicate guard compares project too (`api.ts:194-196`). registrationWorkspace selects mapping rows without DISTINCT and accepts only matches.length === 1 (`outbox.ts:182-185`). With QLL and WEB both mapped to repo 555, installation 1, workspace ws, both rows prove the same workspace, but the stored workspace becomes NULL. Production GitHub inboundHandler supplies no workspace in deliveryScope (`reducers.ts:31-35`), so an ordinary referenced PR's linkback comment (`pr.ts:283`) reaches this inference and is terminally refused by mappings.ts:84. Adding the second project therefore breaks valid GitHub writes; replay preserves the NULL ownership and cannot repair them. The new regression explicitly encodes this erroneous case as ambiguous after adding another project in the same workspace (`tests/github/review-r5-cb.test.ts:233-238`).
Fix: Infer from distinct authorized workspace slugs, not the number of project mappings, and/or enter the verified mapping's workspace scope for each reducer. Continue freezing ownership at registration and rejecting genuinely unresolved authority. Replace the same-workspace ambiguity assertion with successful real reducer dispatch for two project mappings.

### F4 [BLOCKING] Check and deployment rollups can write into a former workspace after installation movement
File: src/app/checks.ts:18
Spec: §8, §9, §7.4
Evidence: linkedTargets selects every active link for the repo/PR without mapping.workspaceSlug; putLink then registers each returned target's own slug (:19,25). Concrete supported configuration change: repo R has a linked PR item in workspace old; the instance admin removes R's installation allow-list entry, allows it in workspace new, and old's admin deletes the disabled R mapping (`api.ts:235-238,531-554`). sync_links survives because it has no mapping FK (`001-init.sql:1-15`). Old's target project also has a valid mapping to another repo S. A later R check_suite or deployment_status is admitted through R's new mapping, yet linkedTargets returns the old target. Its standalone upsert_rollup stores slug old but no source repo/installation (`outbox.ts:692-693`). createOutboundAuthoriser checks old's target project, finds S's authorized mapping (`mappings.ts:131-135`) and permits the write. R's event has now crossed the moved installation's workspace boundary and can overwrite old's development data. CA identified the missing filter in its write-up; the committed test deletes the foreign control link before running checks (`tests/app/review-r5-ca.test.ts:157-159`), so its isolation assertion cannot cover this path.
Fix: Scope linkedTargets to mapping.workspaceSlug. Persist and validate the actual source mapping/repository/installation on every standalone Plane intent, including rollups, so an unrelated target mapping cannot grant authority after source revocation/removal. Cover installation movement plus deletion of the old mapping while retaining the old sync_link and an unrelated authorized target mapping.

### F5 [MAJOR] PR events after terminal create failure still disappear before workflow replay
File: src/app/pr.ts:178
Spec: §4, §6, §7.1, §7.4, §7.6
Evidence: Opened with QLL-NEW registers its create. A prolonged Plane outage exhausts the outbox retry window before an item/link is saved; failIntent fails the group and deletes its pending_sync_links marker (`outbox.ts:446-448`). The PR then merges while the failed workflow awaits operator repair. handleForMapping finds no ordinary references or active links, skips createRequested for action closed (`pr.ts:205,224,230`), and deferPendingPr finds no marker and excludes failed groups (:176-178). items is empty and the reducer returns at :244, so processInbound records the merge handled (`workers.ts:115`) without saving a merge continuation. After Plane recovers, replayDelivery restores only the original workflow: its create still carries the started state saved at pr.ts:97, and its continuation still carries the opened job at :100. The created item therefore stays in its initial started state with no registered merge effect. F1 additionally refuses the original resume; fixing that refusal alone would execute the stale opened snapshot (`pr.ts:293,303`), not restore the missing merge or final MERGED rollup. The F6 tests cover pending and post-link/pre-resume states, not a terminal unlinked create (`tests/app/review-r5-ca.test.ts:174,208`).
Fix: Retain event-specific continuations for later PR deliveries against retained failed create roots as well as pending ones, without implicitly retrying failed remote writes. Make explicit repair revive those continuations in delivery order. Cover terminal unlinked failure, a subsequently handled merge, and replay of the original creation; assert the merge rule and final MERGED rollup occur once.
