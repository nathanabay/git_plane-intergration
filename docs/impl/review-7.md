## Findings

### F1 [MAJOR] Push and PR freeze the previous installation before their own installation refresh
File: src/app/push.ts:34
Spec: §4, §7.2, §7.4, §8, §9
Evidence: Concrete supported transition: a verified mapping stores installation 1; installations 1 and 4242 are both allow-listed for the same workspace; the next authenticated repository delivery carries installation.id 4242. The service explicitly supports remembering that update (`context.ts:114-120`; existing fixture `tests/a8/reducers.test.ts:151-164`). handlePush freezes installation 1 at :34, then calls ensureLinkedByEmail at :35. For a human sender with no existing link, that lookup calls installationFor with the payload (`identity.ts:66`), which saves 4242 on the database mapping and mutates the in-memory mapping. Even a successful profile lookup with no public email then returns normally (:69). The subsequent Smart Commit is registered with the already frozen installation 1; mappings.ts:115 finds no matching source row and outbox.ts:537-538 makes the refusal terminal. The SHA/step is already registered/claimed, so ordinary retry skips it, and explicit Retry/replay cannot authorize the saved installation 1. PR handling has the same order: mappingWriterContext freezes at pr.ts:162, while actorTokenFor/reviewsOf/linkback later invokes installationFor with the payload (context.ts:99; pr.ts:48,280,295). State/rollup intents keep the old snapshot, and a GitHub linkback using 4242 is rejected at freezeAuthority's installation mismatch (`outbox.ts:200-201`). Issue/check reducers resolve the installation before freezing; push and PR do not. The new interleaved Smart Commit fixture uses an unchanged installation and misses this transition.
Fix: Resolve and authorize the delivery's installation before entering the frozen writer/scope context in push and PR, as issue/check reducers already do. Preserve that admitted snapshot for subsequent registrations and resumed work; do not rewrite already stored authority. Cover a 1-to-4242 allowed update through actual push and PR reducers, with an unmapped sender and production outbox authorization, and require once-only state/comment/rollup/linkback execution and repair.

### F2 [MAJOR] A failed PR tail permanently fences new requests after its partner is confirmed orphaned
File: src/app/pr.ts:175
Spec: §1.3, §6, §7.6
Evidence: QLL-NEW creation succeeds, commits its sync_link and created audit, then the original resume_reducer fails terminally; failIntent removes the live marker (`outbox.ts:478-480`). The created Plane item is subsequently deleted and reconciliation marks that exact link orphaned. On a fresh edited/reopened QLL-NEW request, deferPendingPr still discovers the old root solely because any member is failed (:174-176); it never checks whether the saved create result's partner is orphaned. It adds QLL to deferred.identifiers (:193), appends a held continuation against the deleted item (:198-203), and handleForMapping filters QLL out before createRequested (:245). Thus createRequested's confirmed-orphan guard/generation path (:80,89) is unreachable, even though nextCreateGeneration explicitly permits replacement when the orphan matches the saved result (`mirror.ts:133-152`). Repeated fresh requests only add more held continuations; retrying the old group retains the deleted issue ID and cannot create a replacement. The new F5 test starts with an unlinked failed create, while the earlier PR replacement test starts with a fully completed workflow; neither covers their intersection.
Fix: Exclude confirmed-orphan workflows from the failed-create event fence when their saved create result identifies that orphan, and let a fresh create request reach the existing replacement-generation policy. Continue retaining ambiguous/unlinked failures under their old identity and guarding original-delivery replay. Cover successful creation, terminal tail failure, actual reconciliation orphaning, fresh -NEW request and repeated replay; require one distinct replacement partner.

### F3 [MAJOR] New orphan comments omit frozen authority and can adopt another mapping after source deletion
File: src/app/main.ts:211
Spec: §1.3, §8, §9
Evidence: linkbackOnOrphan selects an allowed mapping, but sends its new GitHub comment through the raw ctx.github.apply without stamping _authority or entering a mapping scope (:209-214). Maintenance runs outside inbound deliveryScope. With two mappings A and B for the same repository/installation/workspace and different projects, A is the selected mapping when its orphan comment is queued. registrationWorkspace can infer the workspace, but freezeAuthority finds no source snapshot (`outbox.ts:191-193,283-285`). Delete A before execution while B remains authorized. The authorizer takes the legacy branch and accepts B by repo/installation (`mappings.ts:130-132`), so the comment is emitted after its actual source mapping has been removed. This is a newly registered production intent, not an older row entitled to legacy checks; it contradicts the round-6 contract's immutable source-mapping ownership. CB explicitly relayed the missing main.ts stamp in its write-up, but committed main.ts still contains the raw call. Frozen PR/mirror/check intents correctly refuse the equivalent deletion.
Fix: Stamp freezeMappingAuthority(mapping) on orphan-comment registration, or use the shared mapping writer context after installation resolution. Keep legacy behavior limited to genuinely older unstamped rows. Exercise the real maintenance callback with production outbox authorization, delete its admitted mapping while leaving another eligible repo mapping, and require execution and Retry to refuse without sending a comment.
