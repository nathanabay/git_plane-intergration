## Findings

### F1 [MAJOR] UI replay does not reset failed create-plan tails through the real reducers
File: src/sync/mirror.ts:164
Spec: §7.6, §7.3, §6
Evidence: Static trace: let a mirror create and its sync_link succeed, then its cross-link comment fail permanently. failIntent cancels the remaining siblings and removes the marker (`outbox.ts:398-400`). Replaying the original inbound_delivery retains its writeDeliveryId, but onGithubIssue now finds the active link, handles the label event as an ordinary update, and never calls the original create plan. Consequently `plan`'s replay reset (`outbox.ts:332`) is unreachable and the failed comment/continuation stays failed. A PR has the same gap: the create/link/created audit commit before its resume; after that resume fails, createRequested skips at the created audit (`pr.ts:64-65`). The outbox tests at `tests/writers/review-r4-cb.test.ts:80-105` call plan directly with the old key; they do not exercise either reducer replay. The manual retry endpoint is wired correctly, but the UI has only inbound replay (`Workspace.tsx:660-665`).
Fix: Bind original deliveries to their registered workflow roots and have explicit replay reset those roots before active-link/created-audit shortcuts. Preserve successful steps and their results. Exercise both actual reducers after a failed tail, including the original rule continuation.

### F2 [BLOCKING] A fresh generation discards ambiguous-create identity and can create a second Plane partner
File: src/sync/mirror.ts:118
Spec: §5, §7.3, §6
Evidence: Static failure trace: a create POST commits in Plane, but its response is lost. Same-intent recovery is correct while that outbox row remains pending. If recovery GETs stay unavailable until retry exhaustion, failIntent records a failed group and deletes its marker, with no local active link. The next opt-in, including explicit replay, reaches nextCreateGeneration and unconditionally returns a different key for a failed finished group (`:108-118`). That hashes to a different root and create-step head.id. PlaneWritePath queries only external_id equal to the new intent and posts that new external_id (`plane.ts:346,368-369`), so it cannot recover the already committed old item. Both items can exist, while migration 007 only constrains local active links after creation. This also applies to PR creates that failed before their created audit. The generation tests simulate a definitively failed database state (`review-r4-cc.test.ts:163-165`), and the Plane tests cover recovery with an unchanged intent, leaving their intersection uncovered.
Fix: Separate an intentional replacement of a confirmed orphan from recovery of a failed/ambiguous create. Replay must reuse the original workflow/intent. Before advancing a failed unlinked generation, recover its saved create result or old external_id and prove the old partner absent; unavailable lookup must defer generation advancement. Cover a committed-but-unacknowledged POST followed by terminal failure and re-opt-in.

### F3 [BLOCKING] NULL installations and queued intents bypass installation revocation
File: src/app/mappings.ts:36
Spec: §8, §9
Evidence: The SQL explicitly permits installation_id IS NULL. This includes all pre-003 mappings and even new POST /mappings rows, whose insert omits installation_id (`api.ts:197-201`). Remove or move an installation's allow-list entry before such a mapping's first delivery: mappingsForRepo/project still returns it. installationFor takes the event's installation or resolves it, remembers it, and returns it without checking workspace_installations (`context.ts:114-122`); the current delivery then registers writes across the forbidden workspace boundary. Later deliveries being filtered does not undo the first one's writes. A second gap remains for previously registered writes: DELETE /instance/installations removes only the allow-list row (`api.ts:550-553`), while the outbox executes stored installationId/workspace_slug without any allow-list query. A queued create can therefore disclose a Plane item's content to a removed/moved installation after revocation. The F5 tests seed non-NULL installation IDs and inspect new lookups, rather than these boundaries.
Fix: Resolve and authorize NULL installations before admitting a mapping, persist the verified installation during mapping creation/change, and fail closed on an unlisted or differently owned resolved installation. Re-check installation/workspace authority when executing or retrying durable cross-system writes. Expose the upgrade's disabled/unresolved mappings to the instance admin. Cover first-use and already-queued revocation.

### F7 [BLOCKING] Concurrent auto-link can resurrect an account after a successful unlink
File: src/ui/api.ts:347
Spec: §9
Evidence: DELETE performs three separately committed operations: remove user_map (`:347`), insert the tombstone (`:350`), then revoke tokens (`:353`). There is no shared transaction/lock with ensureLinkedByEmail. A valid interleaving is: DELETE removes the map; an incoming event sees no map and no tombstone, completes its final tombstone SELECT (`identity.ts:62`); DELETE inserts the tombstone and revokes tokens; the event inserts user_map (`identity.ts:63-65`); DELETE returns 204. All queries succeed, but the user is linked again. Even a transaction around DELETE alone would not serialize a prior final tombstone read and subsequent INSERT. Future ensureLinkedByEmail calls return the existing row before checking the tombstone (`:35-36`), so the resurrected mapping persists, drives assignee/actor resolution, and can use a subsequently stored PAT. A failure between deletion and tombstone insertion also leaves no durable suppression. The new tests are sequential.
Fix: Serialize unlink, manual link and auto-link decisions with the same workspace/account lock; transactionally change the map and tombstone (and revoke tokens for unlink) on a dedicated connection. Check tombstone authority before returning existing mappings, and fail closed on suppression-read errors. Cover the final-check/insert race and rollback of each unlink mutation.

### F8 [BLOCKING] The default deployment cannot persist the retired-credential marker across restart
File: src/app/credentials.ts:63
Spec: §8, §9, §4
Evidence: The default marker is beside GITHUB_PRIVATE_KEY_PATH (`:29`), which the example sets to /run/secrets/github-app.pem. Dockerfile runs as USER node; compose bind-mounts only that PEM read-only and supplies no writable persistent credential-state directory. remember silently swallows a marker write failure (`:51`). On container restart/recreation, sawRow, lastRow and cached are empty and that marker is absent. With Postgres temporarily down, the SELECT throws and the catch returns fromEnvironment (`:56-63`) without being able to consult migration 007's github_credential_state. Therefore an environment webhook secret retired by an admin rotation becomes accepted again, despite the database marker. HTTP starts before migration/recovery (`main.ts:128,138`), so the gap is reachable; Valkey can queue a forged delivery signed with the retired secret for processing once Postgres recovers. The restart test uses a writable temporary key directory and asserts the file exists (`tests/ui/review-r4-sb.test.ts:64-78`), unlike production.
Fix: Make the bootstrap-retirement flag durable on a configured writable persistent volume, wire that location in production, and refuse verification on a cold database outage when retirement cannot be established safely. Do not silently treat a failed mandatory marker write as durable protection. Cover the real read-only-secret/non-root deployment and container recreation, with the database unavailable and an old-secret signature.

### F9 [MAJOR] Claimed Smart Commits bypass replay reset and have no failed-write UI action
File: src/github/smart-commits.ts:341
Spec: §5, §7.2, §7.6
Evidence: Production writer.apply acknowledges durable registration immediately (`outbox.ts:253-257`), so a Smart Commit step is audited applied at `:359` and its SHA is claimed at `:430` before the Plane worker actually executes it. Durable registration can safely own once-only execution, but when that intent later becomes failed, replaying the original push returns skipped at the recorded/claimed guard (`:341`) before writer.apply can invoke resetFailed. Merely retaining writeDeliveryId in the scope does not reset the row. The new authorized retryFailed API does repair failed rows by ID, but AuditLogPage renders an action only for inbound_delivery and calls only /audit/:id/replay (`Workspace.tsx:660-665`); outbound_write_failed rows have no repair button. A user's terminally failed #comment/#done therefore remains lost after the UI's replay reports success. This is the precise remaining incompatibility with the brief's exactly-once/recoverable Smart Commit requirement.
Fix: On explicit replay, revive failed intents belonging to the original SHA/step identities before honoring completion shortcuts, without replaying successful effects. Distinguish registered from executed command outcomes in the audit. Add a workspace-scoped failed-write Retry action using the wired endpoint and expose eligible failures. Cover the real push reducer and UI path after terminal failure, including one successful sibling command.

### F11 [MAJOR] Readiness swallows a throttled 403 instead of retrying its final signal
File: src/github/pr-automation.ts:300
Spec: §7.1, §9
Evidence: fetchCombinedStatus classifies every 403 as unavailable permission and returns null (`:298-302`); it never inspects retry-after or x-ratelimit-remaining. The production Octokit error carries those headers, as the corrected installation lookup and outbox classifiers already recognize. An approved PR's last check_suite.completed/status-success event can encounter a secondary-rate-limit 403 here; fireReadyForMerge audits an App-permission error and returns false, so the inbound job succeeds with no retry. When throttling clears, there need be no further GitHub event to reevaluate readiness. The rule never fires although the PR is ready. The F6 fix tests only bare 403/404 plus 5xx and misses the transient-403 branch.
Fix: Distinguish rate-limited 403s before the permanent-unavailable branch and propagate/delay them using the normal retry path and headers. Keep ordinary permission failures fail closed. Cover retry-after and exhausted-quota responses on the final readiness signal, followed by recovery.
