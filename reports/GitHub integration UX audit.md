# Our sync out-automates Plane but hides itself

Our self-hosted Plane v1.4.2 ↔ GitHub service already has a stronger automation engine than Plane's official integration and most of the reference products. Its weakness is that users can't see that engine working. The engine offers ten lifecycle points, branch-aware rules, per-field conflict policies, Smart Commits, a replayable audit log and a rules dry-run. The surface around it is two admin-only iframes built on raw UUIDs, free-text `group:Name` states and JSON, with nothing native on the Plane work item and no health signal a workspace admin can read. The eight-task parity plan (C1–C8) fixes the setup and identity half of the gap: the Connect button, personal OAuth, the repo picker, open/closed states, cross-links, mentions, issue references and GitHub Enterprise. It does not touch the two problems users of the reference products complain about most. The first is "connected, but nothing syncs and I can't tell why": GitHub for Atlassian sits at **3.34 stars over 508 reviews**, and its recent 1-star reviews say exactly that. The second is failures that happen silently, away from the place the user is working. Ranked by user impact, the highest-value new work is (1) a per-mapping sync-health surface for workspace admins, (2) in-context failure feedback on the PR, commit or work item, (3) a native "Development" panel on the Plane work item with copy/create-branch, and (4) replacing raw identifiers with pickers and names across the admin UI. All four sit outside the parity plan. Every one of them is mostly a presentation layer over data the service already records.

## Every reference product converges on the same five-part shape

Plane's official integration is the baseline users will compare us against, and it is narrower than its marketing suggests. It is **commercial-only (Pro, Business, Enterprise)**. Community-edition self-hosters get a "Not Authorized" view at `/settings/integrations/`, and a Plane staff member confirmed integrations are "available only for Pro and Business plan users" ([makeplane/plane#7269](https://github.com/makeplane/plane/issues/7269)). Inside the paid tiers, a workspace Admin clicks **Connect** under Workspace settings → Integrations → GitHub, installs the GitHub App on an org, and lands back on a page with three sections: org connection, personal account, and per-project mappings ([Plane docs](https://docs.plane.so/integrations/github)). The mapping modal ("Link GitHub Repository to a Plane Project") picks a project and repository, maps only **Issue Open** and **Issue Closed** to Plane states, and chooses Unidirectional or Bidirectional sync. A separate PR state mapping covers six events: Draft Open, Open, Review Requested, Ready for Merge, Merged and Closed. It has one guard, "Prevent issues from moving to an earlier state due to PR updates" ([Plane i18n strings](https://github.com/makeplane/plane/blob/preview/packages/i18n/src/locales/en/integration.json)). Only bracketed references like `[WEB-344]` drive state changes, and users call this a burden that "breaks down as soon as anyone forgets" ([makeplane/plane#9056](https://github.com/makeplane/plane/issues/9056)). Issue mirroring is label-gated (`plane` on GitHub, `github` on Plane) and posts cross-link comments on both sides. In May 2026 a user filed six markdown-fidelity bugs covering mentions, `#NNN` refs, images, tables, bare URLs and soft wraps, under a meta-issue titled "silently overwrites GitHub bodies with corrupted markdown". Plane closed the meta-issue in August as fixed ([makeplane/plane#9077](https://github.com/makeplane/plane/issues/9077)). Plane has **no sync log or status UI**. The 2023 request to "show github sync status/log/errors" was closed without one shipping ([makeplane/plane#1622](https://github.com/makeplane/plane/issues/1622)).

The other products fill in what Plane leaves out, and they agree on five things. The first is a **scope split**. Linear puts the install, linkbacks and commit linking at workspace level, status automation and per-target-branch regex rules at team level, and connected account, branch copying and notifications at personal level ([Linear docs](https://linear.app/docs/github); [Linear Code & reviews](https://linear.app/docs/code-and-reviews)). The second is **self-service identity**. Linear shows "a banner in the GitHub integration settings" to members who haven't linked an account ([Linear docs](https://linear.app/docs/github)). ClickUp lets any member create a personal OAuth connection ([ClickUp Help](https://help.clickup.com/hc/en-us/articles/6305771568791-GitHub-integration)). The third is **branch helpers on the ticket**. Linear has a configurable Branch format and **Copy git branch name** (`Cmd/Ctrl+Shift+.`), which can also move the issue to started. Jira has **Create branch / Create commit / Create pull request** in its Development panel ([Atlassian](https://support.atlassian.com/jira-software-cloud/docs/view-development-information-for-an-issue/)). Shortcut has Git Helpers with custom Git Branch Formatting ([Shortcut Help](https://www.shortcut.com/help/integrations/github)). ClickUp has an `:taskId:_:taskName:_:username:` template and New GitHub Branch/PR/Issue actions ([ClickUp Help](https://help.clickup.com/hc/en-us/articles/6305771568791-GitHub-integration)). Plane's own request for this, "Create a GitHub Branch From A Work Item", has been open since February 2025 ([makeplane/plane#6611](https://github.com/makeplane/plane/issues/6611)). The fourth is a **native development panel** on the ticket. Jira aggregates PR state by precedence (OPEN > MERGED > DECLINED) with counts and a details dialog. Linear's PR attachment shows reviewer avatars and preview links. Shortcut's Story pane shows review status, build status and PR labels ([Shortcut blog](https://www.shortcut.com/blog/shortcut-vcs-integration)). The fifth is **explicit onboarding handoffs**. Jira's wizard tells a non-owner to "Send them a link and ask them to connect" to an org owner. It runs a 6-month backfill automatically while webhooks stay live, and admins can continue it from a chosen date ([Atlassian connect](https://support.atlassian.com/jira-cloud-administration/docs/integrate-with-github/); [Atlassian backfill](https://support.atlassian.com/jira-cloud-administration/docs/understand-github-for-jiras-initial-backfill-process)).

The references are also consistently weak in one place: telling users what went wrong. Jira reports Smart Commit failures **only by email**, and stays silent when no email matches ([Atlassian Smart Commits](https://support.atlassian.com/jira-software-cloud/docs/process-issues-with-smart-commits/)). Its reviews keep coming back to the same complaint: "all status indicators show that the system is 'connected' … yet no data is synced. There is no way to debug" ([Marketplace reviews](https://marketplace.atlassian.com/rest/2/addons/com.github.integration.production/reviews?limit=30&sort=recent)). A third-party Linear troubleshooting guide says most link failures are ID-matching failures that "fail silently". It also notes that a green "Connected" badge proves only that OAuth worked ([workmanagementhub](https://workmanagementhub.com/linear-github-sync-troubleshooting-2026/)). Linear's mitigation is a sync-error banner on the issue itself ([Linear docs](https://linear.app/docs/github)). This shared weakness is where a self-hosted service with a full audit trail can most clearly beat the incumbents.

## Where our service already beats every reference

Several things that look like gaps in our UI sit on top of capabilities the references lack entirely. The rules engine exposes **ten lifecycle points**: Branch pushed, PR drafted, opened, review requested, changes requested, approved, ready for merge, merged, closed without merge, and reopened. Plane has six and Linear five. It adds a merged-base-branch regex and a "Branch-aware rules" table ([src/ui/client/Workspace.tsx:255-266,448-521](../src/ui/client/Workspace.tsx)). Plane offers nothing per-branch, so this matches Linear's per-target-branch rules and goes beyond Plane. **Per-field conflict policies** cover title, description, state, assignees, labels and comments, each set to last-write-wins, GitHub-wins or Plane-wins ([src/ui/client/Workspace.tsx:213-248](../src/ui/client/Workspace.tsx)). No reference offers anything like it. Plane's only conflict controls are the direction toggle, an overwrite warning and the "earlier state" checkbox. We have **configurable magic-word tiers** (closing, non-closing, relation) and `KEY-NEW` creation, plus `skip`/`ignore` opt-outs ([src/ui/client/Admin.tsx:238-280](../src/ui/client/Admin.tsx); [src/parse/references.ts:57](../src/parse/references.ts)). Together these reproduce Linear's linking grammar and avoid the bracket requirement Plane users complain about. **Smart Commits** support `#comment`, `#time` and `#transition`, with an optional signed-commit gate ([src/github/smart-commits.ts:398,484-496](../src/github/smart-commits.ts)). Plane's official integration has nothing comparable.

Operationally, our tooling is ahead of every product surveyed. Neither Jira nor ClickUp has a per-event delivery log ([Atlassian FAQ](https://support.atlassian.com/jira-cloud-administration/docs/github-integration-faq/); [ClickUp Help](https://help.clickup.com/hc/en-us/articles/6305771568791-GitHub-integration)), and Plane has none ([makeplane/plane#1622](https://github.com/makeplane/plane/issues/1622)). We have an **audit log with Replay on inbound deliveries and Retry on failed outbound writes**, a **dry-run** of rules against recorded deliveries, and a **backfill that reports counts** ("Checked N pull requests and M issues: X links made, Y references did not match") instead of a bare status word ([src/ui/client/Workspace.tsx:632-782](../src/ui/client/Workspace.tsx)). The work item also gets CI, deploy and preview links (`[CI] Build · pass`, `[Deploy] env · state`, `[Preview] Vercel`) ([src/app/checks.ts:165,266,274](../src/app/checks.ts)). Plane's official docs describe none of these. A reconcile sweep catches missed webhooks, and echo suppression prevents sync loops. Finally, the service runs on the free self-hosted edition, which Plane's own integration does not support at all. The UX work below should therefore surface what the service already knows, not rebuild it.

## The parity plan covers the setup and identity half

The eight known gaps rank high on user impact, and the plan's designs line up with the references. **C1 (Connect, install and return)** replaces today's runbook. Today an instance admin must find a numeric installation id on GitHub and type it against a free-text workspace slug ([src/ui/client/Admin.tsx:203-233](../src/ui/client/Admin.tsx)), the step Plane, Linear, Jira and Shortcut all handle with one button. **C2 (personal OAuth)** fixes the fact that plain members have no entry point at all. The Plane fork gates the settings page to role 20 ([packages/constants/src/settings/workspace.ts:67-71](../packages/constants/src/settings/workspace.ts)). C2 also fixes attribution: `TokenVault.store` has no caller, so every write is authored by the bot ([src/auth/identity.ts:135-146](../src/auth/identity.ts)). **C3 (repo picker)** replaces typed `owner/repo` plus "Look up id". **C4 (open/closed states)**, **C5 (cross-links)**, **C6 (mentions)** and **C7 (issue references)** bring mirrored-issue content up to Plane's documented sync table. **C8** separates ghe.com from GHES.

Within that scope, four refinements are worth folding into the plan before it starts. First, C1 should copy Jira's **owner handoff**. When the workspace admin isn't a GitHub org owner, the GitHub install becomes a request rather than an install. Jira handles this with a "Send a link to an organization owner" dialog, and the owner approves through **Approve & Install** ([Atlassian](https://support.atlassian.com/jira-cloud-administration/docs/integrate-with-github/)). Without it, C1 dead-ends for most admins. Second, C2 should add Linear's **unlinked-member banner** and a visible "needs re-authorization" state on the user's own row. The plan already falls back to the service identity when a refresh fails, but it says nothing about telling the user. Third, C6 and C7 should borrow Plane's fidelity bug list as test cases: tables, image alt text, bare URLs and soft wraps alongside mentions and refs ([makeplane/plane#9077](https://github.com/makeplane/plane/issues/9077)). Our own `htmlToText`/`textToHtml` round-trip has not been assessed. Fourth, C4 puts a state dropdown in the mapping dialog, but the far larger state-entry surface, the ten-row lifecycle table with free-text `started:In Progress` strings ([src/ui/client/Workspace.tsx:418-446](../src/ui/client/Workspace.tsx)), stays untouched. It should reuse the same dropdown (see N4 below).

## Seven new gaps the plan does not cover, ranked by user impact

The table ranks every gap together, so the plan's tasks and the new ones can be scheduled against each other. Impact means how often a user hits the problem and whether it blocks them or only slows them down. "New" marks gaps outside C1–C8.

| Rank | Gap | Who feels it | Plan | Build |
|---|---|---|---|---|
| 1 | No sync health visible to workspace admins; key failure signals invisible anywhere | Workspace admin, every day | **New (N1)** | Per-mapping health card and instance audit view |
| 2 | Connect requires an operator runbook (C1) | Every new workspace | C1 | As planned, plus owner handoff |
| 3 | Members can't link accounts; everything is authored by the bot (C2) | Every member | C2 | As planned, plus banner |
| 4 | Failures reported only in the audit log, never where the user acted | Developers | **New (N2)** | PR/commit replies, item comments |
| 5 | Nothing native on the Plane work item; no copy/create branch | Every developer, every ticket | **New (N3)** | Fork-patched Development panel |
| 6 | Raw UUIDs, free-text states, internal jargon across the admin UI | Workspace and instance admins | **New (N4)**; C3/C4 partial | Pickers and name resolution |
| 7 | Repo picker, open/closed states, cross-links, mentions, refs (C3–C7) | Admins and members | C3–C7 | As planned |
| 8 | Backfill not offered at mapping time; no first-run guidance | New mappings | **New (N5)** | Post-save prompt and setup checklist |
| 9 | UI silently overrides or hides settings | Admins | **New (N6)** | Bug fixes and small UI additions |

**N1. Workspace admins cannot tell whether sync works.** This ranks first because it is the problem users of the reference products complain about most, and our service already holds the data to fix it. The workspace mapping list carries no disabled, installation or health field. A mapping disabled because its installation was removed from the allow-list looks normal to the workspace admin, and only the instance page lists it ([src/ui/api.ts:149-159](../src/ui/api.ts); [src/ui/client/Admin.tsx:28-48](../src/ui/client/Admin.tsx)). The silent-Plane-webhook detector writes `plane_webhook_silent` rows with no workspace slug and no error. The workspace audit view filters those rows out, and the health failure count doesn't include them either, so a disabled Plane webhook surfaces only as a server log line ([src/sync/reconcile.ts:169-171](../src/sync/reconcile.ts); [src/ui/api.ts:411-419](../src/ui/api.ts)). The health API returns `githubAppCredentials.decryptOk`, but the UI never renders it, even though a decrypt failure makes every GitHub webhook fail with 503 ([src/ui/api.ts:620-644](../src/ui/api.ts)). "Database: reachable" is hard-coded true. "Failures in the last 24 hours" counts every errored row instance-wide, and there is nowhere to click through to them, because no instance audit view exists ([src/ui/api.ts:621,632-638](../src/ui/api.ts)). The fix is a **health card on each mapping row**. It shows last GitHub delivery, last Plane delivery, last successful write, errors in the last 24h (linked to a filtered audit view), a Disabled badge with its reason, and a rate-limited-until time. Add a **workspace banner** when the Plane webhook is silent or App credentials fail to decrypt. Add an **instance-level audit tab** for the unattributed rows. Linear's issue-level sync banner and the Jira reviewers' demand to distinguish "connected" from "data flowing" set the bar ([Linear docs](https://linear.app/docs/github); [Marketplace reviews](https://marketplace.atlassian.com/rest/2/addons/com.github.integration.production/reviews?limit=30&sort=recent)).

**N2. Failures happen silently from the developer's point of view.** Several failures reach only the workspace audit log, which developers can't open. They include a Smart Commit transition matching no state or several states, a malformed `#time`, an unsigned commit whose commands are ignored, truncation on large pushes, an unresolved reference, an identity email-match failure, and missing "Commit statuses: Read" for merge readiness ([src/github/smart-commits.ts:72-78,250-284,344-350](../src/github/smart-commits.ts); [src/app/pr.ts:198](../src/app/pr.ts); [src/app/identity.ts:69](../src/app/identity.ts)). This repeats the anti-pattern that hurts Jira, which emails failures or drops them, and the silent link-matching failures reported for Linear. We can do better than both. When a PR references a key that resolves to nothing, post (or edit in place) one bot comment on the PR. When a Smart Commit fails, post one commit comment explaining why. When an automation fails against a known item, add a Plane comment on that item. All three should sit behind a per-mapping "Report problems on GitHub/Plane" toggle that reuses the linkback toggle's model, since Linear treats linkback noise as a real complaint and makes it switchable ([Linear docs](https://linear.app/docs/github)).

**N3. Nothing native appears on the Plane work item.** The fork patches seven files, and none of them touches the work-item page ([apps/README.md:7-19](../apps/README.md)). All dev info therefore lands as text-prefixed rows in Plane's generic Links section, such as `[PR] #12 Title · OPEN · REVIEW` and `[CI] Build · pass` ([src/sync/dev-info.ts:12-56](../src/sync/dev-info.ts)). The spec's "copyable branch name and branch creation from an issue" (§7.1) and its icon rendering were never implemented ([spec](../docs/superpowers/specs/2026-10-10-plane-github-sync-design.md), lines 325-327 and 406-411). Branch helpers are the one feature every reference has, and Plane's own users are still asking for it ([makeplane/plane#6611](https://github.com/makeplane/plane/issues/6611)). Build it in two steps. First, a **branch-name template** per mapping (Linear and ClickUp style, required to contain the key). Second, a fork-patched **Development panel** on the work item sidebar, with Jira-style precedence roll-up of PRs (open > merged > declined), check and deploy badges, preview links, **Copy branch name**, and **Create branch** using the installation token. The panel can be an iframe served by our UI, the same pattern the settings pages already use. This keeps the fork small. As an interim measure, add a `[Branch] suggested: …` link when the item is created, so there is something to copy.

**N4. The admin UI makes users handle identifiers machines should handle.** The mapping list shows the Plane project as a raw UUID. User linking requires typing a Plane user UUID ("The user's id in Plane, not their email"). The allow-list takes a free-text workspace slug. Lifecycle states are typed as `group:Name` strings. The hint text cites "§7.1", and the YAML example uses a different state syntax from the table. The audit log shows raw `kind` values and `JSON.stringify(detail)`, including whole webhook payloads ([src/ui/client/Workspace.tsx:55,395-446,560,612,658](../src/ui/client/Workspace.tsx); [src/ui/client/Admin.tsx:206-222](../src/ui/client/Admin.tsx)). C3 removes typed repositories and C4 adds one state dropdown; the rest is new work. Resolve project and member names through Plane's API, the same way the project `<select>` already does. Replace the user-UUID field with a member picker. Use one state dropdown component everywhere a state is chosen. Map audit kinds to human labels and collapse the payload behind a "Show raw" control. Remove the spec-section references from the UI text.

**N5. First-run has no guidance and backfill is hidden.** Saving a new mapping just resets the form. The spec's "on first mapping, optionally scan" prompt was never built, so backfill sits on a separate Settings tab ([src/ui/client/Workspace.tsx:141-144,709-733](../src/ui/client/Workspace.tsx)). Jira imports six months of history automatically and lets admins continue it from a chosen date ([Atlassian backfill](https://support.atlassian.com/jira-cloud-administration/docs/understand-github-for-jiras-initial-backfill-process)). Linear and Plane sync only new issues, and Plane users wrote their own scripts to import comment history ([forum #119](https://forum.plane.so/t/full-imports-of-github-issues-including-comments/119)). After Add mapping, show a step that offers "Link existing open PRs and issues now" with progress. Add an empty-state checklist to the mapping page: rules default, conflict policies default, members linked X/Y.

**N6. The UI silently overrides or hides settings.** These are cheap fixes. The instance default "Enable Smart Commits for newly mapped repositories" never applies to mappings created in the UI, because the form starts the checkbox at `true` and always sends it ([src/ui/client/Workspace.tsx:115,134-137](../src/ui/client/Workspace.tsx); [src/ui/api.ts:239,245](../src/ui/api.ts)). Every UI save resets `autolinks` to false ([src/ui/client/Workspace.tsx:136,177](../src/ui/client/Workspace.tsx)). Rule versions are stored with author and time, but there is no history view or rollback ([src/ui/api.ts:283-314](../src/ui/api.ts)). Dry-run offers three event types while the engine accepts check-suite, deployment, issue and comment triggers ([src/ui/validate.ts:241](../src/ui/validate.ts)). `REQUIRE_VERIFIED_COMMITS` exists only in env, although Linear treats "Require signed commits" as an admin setting in the UI ([Linear Code & reviews](https://linear.app/docs/code-and-reviews)). Fix the default, preserve `autolinks`, add a versions list with "Restore", widen dry-run to every trigger, and expose the signed-commit gate on the admin page.

**N7. Setup steps outside the UI are never verified.** Even after C1, an operator still creates the App by hand, registers the Plane webhook by hand, and aligns two rate-limit values by hand ([deploy/APPLY.md:170-194](../deploy/APPLY.md)). No document lists the GitHub webhook events to subscribe to, and the runtime needs "Commit statuses: Read", which the README's permission list omits ([apps/README.md:32-42](../apps/README.md); [src/app/pr.ts:198](../src/app/pr.ts)). Plane's self-hosting guide does publish the exact event and permission list ([Plane developer docs](https://developers.plane.so/self-hosting/govern/integrations/github)). Jira offers **Automatic app creation** for GHES ([Atlassian GHES](https://support.atlassian.com/jira-cloud-administration/docs/connect-a-github-enterprise-server-account-to-jira-software/)). The cheap fix is to document the event list and add the missing permission. The better fix is a **setup checklist** on the admin page that tests each prerequisite live. It should confirm the credentials decrypt, check the App's granted permissions and events against the required set, show when a signed GitHub delivery and a Plane delivery last arrived, and check that the Plane rate limit matches. Each item should link to its runbook step.

Two uncertainties remain. The notes infer from the env shape that a single `PLANE_WEBHOOK_SECRET` makes serving several Plane workspaces awkward, but `src/api/handler.ts` hasn't been checked, so multi-workspace support should be verified before C1 invites more workspaces to connect. And the notes don't establish whether our engine has Linear's "last linked PR wins" gating, its reverse automation (cancelling an issue closes its PRs), or its private-project redaction in linkbacks ([Linear docs](https://linear.app/docs/github)). Each is worth a quick code check, since they belong in the same user-visible behaviour set.

## Conclusion

The comparison changes what parity should mean here. Plane's official integration is a thin, paid baseline, and our service already exceeds it on automation depth and operability. Finishing C1–C8 makes our setup and identity flows comparable to Plane's. It still leaves us with the failure mode the incumbents are criticised for: a system that reports "connected" while users have no way to see what it is doing. The highest-value move is not more sync behaviour. It is showing the user the state the service already records: health per mapping, failures reported where the developer acted, and dev info and branch helpers on the work item itself.

The work is also cheaper than the plan's own tasks. N1, N2, N4 and N6 need no new GitHub permissions, migrations or OAuth plumbing. They read existing audit rows, health fields and Plane APIs, and they can run in parallel with C1–C3. N3 is the only new item that widens the fork, and serving the panel as an iframe keeps that patch as small as the existing settings pages. Doing N1 and N2 alongside C1 makes the newly reachable connect flow trustworthy for the people now able to use it.
